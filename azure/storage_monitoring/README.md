# Datadog Storage Monitoring for Azure Blob Storage

Two ways to set up blob inventory for Datadog Storage Monitoring. Both do the same thing for each storage account:

1. Create the `datadog-storage-monitoring` container.
2. Add a daily CSV blob inventory rule that writes into that container.
3. Grant the Datadog App Registration **Storage Blob Data Reader** on that container only.

| Method | Use |
|---|---|
| `install.sh` | Run in Azure Cloud Shell (Bash) with the command generated by the Datadog UI. |
| `bicep/azuredeploy.bicep` (compiled to `dist/azuredeploy.json`) | ARM deployment for one subscription, from the CLI or a Deploy to Azure link. |

## ARM template

Edit `bicep/`, then rebuild `dist/` from the `azure` folder (CI fails if `dist/` is out of date):

```bash
bash storage_monitoring/build.sh
```

Deploy one subscription:

```bash
az account set --subscription <subscription_id>
az deployment sub create \
  --name datadog-storage-monitoring \
  --location <any_region> \
  --template-file storage_monitoring/dist/azuredeploy.json \
  --parameters \
    datadogServicePrincipalObjectId="$(az ad sp show --id <client_id> --query id -o tsv)" \
    storageAccounts='[{"name":"<account>","resourceGroup":"<resource_group>","enableLastAccessTracking":true}]'
```

Run `az deployment sub what-if` with the same arguments to preview first.

### Parameters

| Name | Required | Description |
|---|---|---|
| `datadogServicePrincipalObjectId` | yes | Object ID (not client ID) of the Datadog App Registration's service principal. |
| `storageAccounts` | yes | `[{ name, resourceGroup, enableLastAccessTracking?, existingInventoryRules? }]` |
| `workflowId` | no | Datadog UI workflow ID, returned in the outputs. |
| `inventoryContainerName` | no | Defaults to `datadog-storage-monitoring`. |
| `inventorySchemaFields` | no | Inventory CSV columns. |

### Differences from install.sh

- **Existing inventory rules:** an account has a single inventory policy, and the template replaces it. Pass the account's other rules in `existingInventoryRules` to keep them. `install.sh` overwrites them.
- **Last-access tracking:** optional per account (`enableLastAccessTracking`). The template copies the current blob service settings so it doesn't reset them.
- **Unsupported account kinds:** `install.sh` skips accounts that are not StorageV2, BlockBlobStorage or BlobStorage. The template fails on them, so the caller must leave them out.
- **Extra columns:** the template also requests `AccessTierInferred` and `BlobType`. `Snapshot` is left out until the inventory reader handles snapshot rows.

HNS (Data Lake Gen2) accounts are handled the same way as in `install.sh`: block blobs only, no blob versions, no version columns.

### Permissions

The deploying user needs `Microsoft.Authorization/roleAssignments/write` on the storage accounts (Owner or User Access Administrator). Contributor alone is not enough.
